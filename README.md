---

This repository contains GPU-accelerated implementations for computing **upper bounds on the capacity of the Binary Deletion Channel (BDC)** using the **Blahut–Arimoto Algorithm (BAA)**. This software is a supplement to [this work](https://arxiv.org/abs/2604.05867).

The main contributions of this repository are:

- Several algorithmic optimizations of the Blahut–Arimoto algorithm for the Binary Deletion Channel.
- Massive GPU parallelization using CUDA.
- The ability to study significantly larger parameter regimes than would be practical with a straightforward implementation.

---

## Install CUDA

The code for the BAA was written in CUDA, and so it is only executable on NVIDIA GPUs. If you do not have the CUDA toolkit installed yet, run:

> sudo apt install nvidia-cuda-toolkit

## Problem Setting

Before we describe the software in more detail, we give some context about the problem we are interested in. We study the binary deletion channel, denoted by BDC_{n,k}:

- An input binary string of length `n` is transmitted.
- The channel uniformly at random selects `k` positions.
- The selected bits are retained in their original order, while all remaining bits are deleted.
- The output is therefore a binary string of length `k`.

The objective is to compute upper bounds on the channel capacity C_{n,k}. Combined with the theoretical results presented in the [companion paper](https://arxiv.org/html/2604.05867v1), these estimates yield upper bounds for the capacity of the classical Binary Deletion Channel with deletion probability d.

If you want to compile and run the program, follow the instructions in the [Compilation](#compilation) and [Running the Blahut–Arimoto Algorithm](#step-2-running-the-blahutarimoto-algorithm) sections.

## Repository Structure

We provide a description of the folders and files in the repository.

### `backend/`

This folder contains the complete GPU implementation of the optimized Blahut–Arimoto algorithm.

#### `BAA.cu`

- Implements the optimized Blahut–Arimoto algorithm.
- Performs the computationally intensive steps on the GPU using CUDA.
- Includes several implementation and algorithmic optimizations.
- For implementation details, see the accompanying paper and the comments throughout the source code.

The `total_transitions` method used to compute transition counts based on the caches is closely based on a prior implementation of Roni Con and Ittai Rubinstein that can be found at [their GitHub repository](https://github.com/ittai-rubinstein/BDC_Upper_Bounds), , accompanying [their paper](https://arxiv.org/abs/2305.07156).

#### `generate_bit_transition_cache.cpp`

- Generates cache files named `cache_n_k`.
- Cache files are stored in the `transition_counts/` directory.
- Each cache stores the number of occurrences of every output string `y` as a subsequence of every input string `x`. More precisely, each cache stores a sequence of integer counts separated by spaces. The counts are ordered according to the lexicographic ordering on the pairs (x,y). In particular, the first integer corresponds to the pair (x=0...0, y=0...0) and the last integer corresponds to the pair (x=1...1, y=1...1).
- These cached transition counts are later used to efficiently reconstruct transition probabilities during the Blahut–Arimoto iterations.

The code used to generate these caches is closely based on a prior implementation of Roni Con and Ittai Rubinstein that can be found at [their GitHub repository](https://github.com/ittai-rubinstein/BDC_Upper_Bounds), accompanying [their paper](https://arxiv.org/abs/2305.07156).

#### `utils.cc` and `cache_io.h`

Provide utilities for:

- loading transition cache files,
- loading and saving distributions,
- memory management for cached data.

#### `main_BAA.cu`

Main entry point for running the Blahut–Arimoto algorithm.

The user can configure:

- the input length `n`,
- the output length `k`,
- the convergence tolerance `a`,
- whether to start from a uniform distribution or a previously saved distribution (`read_from_file`). If one wants to start from a uniform distribution, set this parameter to `0`, otherwise set it to `1`. For more on how to start the execution from a previously saved distribution, see [Restarting from a Saved Distribution](#restarting-from-a-saved-distribution).
- `save_iterations`, which means every `save_iterations` iterations the input distribution is saved.

All these parameters are set in the terminal (see [Step 2: Running the Blahut Arimoto Algorithm](#step-2-running-the-blahut-arimoto-algorithm)).

---

### `transition_counts/`

Stores all precomputed transition-count cache files generated by `generate_bit_transition_cache`.

---

### `distributions/`

Stores input distributions generated by the Blahut–Arimoto algorithm.

These distributions can later be reused to initialize new executions.

## Compilation

**Important:** all executables must be compiled and executed from the repository root (`BDC-Upper-Bounds-GPU`).

The implementation expects cache files and distribution files to be located using paths relative to the repository root. Running executables from another directory will cause loading of cache files and saved distributions to fail.

### Step 1: Compile Cache Generator

First, compile the cache generator by running the following command:

> g++ -std=c++17 -o generate_bit_transition_cache backend/generate_bit_transition_cache.cpp backend/utils.cc

### Step 2: Compile main_BAA.cu

Then, compile the main program by running the following command:

> nvcc -arch=? --extended-lambda -std=c++17 backend/*.cc backend/*.cu -o main_BAA

Replace `?` with the compute capability of your GPU. For example, if your GPU is an RTX 5090, then replace `?` by `sm_89`.

## Running the main program

### Step 1: Generating Transition Cache Files

Before executing the main program, the transition caches must be generated. If you wish to run the BAA on the exact deletion channel with input length `n`, first run the following command to generate all required cache files `cache_n'_k'` for all `1 <= k' < n' <= n`:

> ./generate_bit_transition_cache n

The cache files will be stored in the `transition_counts/` directory.

---

### Step 2: Running the Blahut Arimoto Algorithm

To run the BAA on the exact deletion channel with input length `n` and output length `k` starting from the uniform distribution, with convergence tolerance `a', and saving the input distribution generated by the BAA to disk every 100 iterations of the BAA, run the following command:

> ./main_BAA n k 0 a 100

Alternatively, if you wish to run the BAA from an alternative initial distribution and have the input distributions generated by the BAA saved to disk every `save_iterations` iterations, run the following command:

> ./main_BAA n k 1 a save_iterations

For more on how to run the BAA computation from an alternative initial distribution, see (#restarting-from-a-saved-distribution).

## Program Output

When execution finishes, the program prints the following data in the terminal:

- the approximated channel capacity;
- the final error threshold.

All mutual information values and capacity estimates are reported in **bits**.

If the program outputs:

> approximated capacity = C, 
> error = ε

then the true channel capacity satisfies:

> True Capacity ≤ C + ε.

This guarantee follows from the convergence properties of the BAA, as discussed in the companion paper.

The approximated optimal input distribution is **not printed to the terminal**. Instead, it is automatically stored in the `distributions/` directory. See the [Distribution Files](#distribution-files) section for details.

---

### Structure of Distribution Files

As discussed in the companion paper, binary strings that can be obtained from each other via bitwise complements and string reversals are always assigned the same probability by every iteration of the Blahut–Arimoto algorithm. We group such strings in the same equivalence class, and represent such equivalence classes by their lexicographically smallest element. For example, when *n=4* the strings 0001, 1110, 1000, 0111 are all in the same equivalence class under the operations above, and 0001 is the representative.

Distributions generated by our algorithm are stored in .txt files. Each .txt file contains one floating-point number per line in scientific notation, where the *i*-th line stores the probability assigned to the *i*-th representative in lexicographic order. For example, when *n=4* the line corresponding to 0001 (the second line in the file) stores the probability assigned to the strings 0001, 1110, 1000, 0111 in its equivalence class.

These symmetries reduce the amount of storage required while preserving all information needed by the algorithm.

## Restarting from a Saved Distribution

Computations can be resumed from previously saved distributions. This is especially useful for large problem instances requiring many iterations.

For example, suppose that we have already executed some iterations of the BAA for `n=28` and `k=27`, and an input distribution `dist_28_27.txt` already exists inside `distributions/`.

To restart the BAA from this previously stored input distribution and save a new input distribution to the disk after every `save_iteration` iterations, run the following command:

> ./main_BAA 28 27 1 a save_iterations

More generally, for arbitrary `n` and `k` the distribution you wish to use as the starting point for the BAA must be stored in a file with the name `dist_n_k.txt`, and they must have the same structure as that described in (#structure-of-distribution-files). Otherwise, our program is unable to find the file to read the distribution from. Distribution files generated by our BAA implementation satisfy these formatting constraints by default. 

This functionality is primarily intended for input distributions previously generated by our BAA implementation, to avoid always having to restart computations from scratch.
